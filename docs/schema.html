EcologicalInteraction.participating_taxaTaxonDescriptorWhich members a COMMUNITY_LEVEL interaction is actually about, when it is about some of them rather than all. Optional and usually absent: a statement that genuinely holds across the whole community should leave it empty, and an empty list means "every member", not "none". Exists because the connectivity audit credits a COMMUNITY_LEVEL interaction as connecting every member of the record, which is unavoidably coarse - in a record carrying both kinds of edge, a taxon in no pairwise edge is credited by an unrelated community-level one. Naming participants narrows the credit to them (#312). Not a second way to write a pairwise edge. If an interaction is between two named organisms it wants `source_taxon`/`target_taxon` and PAIRWISE scope; this is for a statement over a named subset, such as three of eight members cross-feeding while the rest do not. Name participants by `preferred_term`, not by CURIE alone. Entries resolve by preferred_term, term.label or term.id, and in strain-level records the id does not identify a member: GLBRC_Populus_Variovorax_SynCom28 has 28 taxa under one NCBITaxon id, so naming two of them by CURIE credits all 28 and the slot appears to do nothing. That is the sound reading of an ambiguous reference, and it is also exactly the record shape where narrowing matters most (#524).
EcologicalInteraction.scopeInteractionScopeEnumWhether this interaction is a pairwise organism-to-organism edge or a community-level/emergent phenomenon. PAIRWISE interactions require a source_taxon. COMMUNITY_LEVEL interactions describe behaviors that emerge from the whole consortium (or are driven by abiotic inputs such as electrolysis-supplied H2) and need not have source_taxon set.

GtdbClassification.curatedbooleanTrue when a curator chose this grounding against what `gtdb_ground.py` computes, so the tool must not overwrite it. The reason belongs in `curation_note`. A hard-coded list in the script protects only what someone remembered to add: `NCBITaxon:340177` (*Chlorobium*) was curated and unlisted, and survived a whole-KB refresh only because its recompute happened to yield no id — a side effect, not a decision (#384). Marking the block keeps the decision with the data.
GtdbClassification.curation_notestringWhy this grounding was curated against the tool. Required in practice whenever `curated` is true — a pin whose reason lives only in a commit message is one re-run away from looking like an error. Enforced by `communitymech.validators.gtdb_coherence`, since a conditional requirement is one of the relations the JSON-Schema backend cannot express (#387).
GtdbClassification.gtdb_idstringCanonical GTDB CURIE (spaces in the taxon name become underscores), e.g. GTDB:s__Bacillus_velezensis or GTDB:g__Agrobacterium. The single letter before `__` is the rank — d, p, c, o, f, g, s — and it is the way to filter by rank. Required, so it is always there to read: the pattern below constrains the value but says nothing when the key is absent, which is why this slot is the one required attribute here (#414 review). **Filter `d__` out of any coverage figure.** The domain groundings (`d__Bacteria`, `d__Archaea`) are true but carry no information beyond the NCBITaxon id, and counting them as "grounded" moves coverage by about seven percentage points (#393, #403). They are not the whole tautological population: a higher-rank grounding whose GTDB name equals the NCBI name at the same rank says as little — `Actinomycetota` -> `p__Actinomycetota`. Filtering on `is_reclassified: false` above genus rank catches those too. Current counts live in `.claude/skills/ground-taxa-gtdb/SKILL.md` and are pinned by `tests/test_gtdb_support_counts.py`, not written here: pythongen drops attribute descriptions, so a count in this text reaches no generated artifact and nothing would fail when it goes stale.
GtdbClassification.gtdb_lineagestringFull GTDB lineage string (domain..species), e.g. "d__Bacteria;p__Bacillota;c__Bacilli;o__Bacillales;f__Bacillaceae;g__Bacillus;s__Bacillus velezensis".
GtdbClassification.gtdb_taxonstringGTDB taxon name (human-readable, spaces preserved), e.g. "Bacillus velezensis".
GtdbClassification.is_reclassifiedbooleanTrue when the GTDB name differs from the NCBITaxon name at the rank this block is grounded at. A string comparison, and nothing more, so the name is a poor guide to what it holds. It said "species name ... (a GTDB reclassification/rename)". Neither half held. Of the 138 blocks currently true, 41 are grounded above species — through genus, family, order, class and phylum — so the rank is wrong for nearly a third of them. And it does not mean GTDB reclassified anything. Partitioning the 138 by why the names differ (#441): * 0 dropped strain designations. There were 40 — `Escherichia coli K-12` -> `Escherichia coli` — and #480 removed them: GTDB carries no strain suffixes, so the names differed while the placement did not. `name_differs` now treats that as no difference. * 32 GTDB polyphyly suffixes — `Bacillota` -> `Bacillota_A`. A split marker on the same name, not a rename. * 13 that are both at once — `Buchnera aphidicola BCc` -> `Buchnera aphidicola_F`. * 3 GTDB placeholders for an unnamed species within the same genus — `Dyadobacter sp.` -> `Dyadobacter sp017744695`. * 3 rank-appropriate nomenclatural endings on one stem — `Chlorobiota` -> `Chlorobiia`, `Nitrososphaerota` -> `Nitrososphaeria`. * 87 genuinely different names, and only some of those are GTDB reclassifications. `Allobosea` -> `Bosea` is an *NCBI* rename: both databases place the organism in the same genus concept, and NCBI moved its label because the bacterial name was a later homonym of the plant *Bosea*. Orthographic and gender variants also sit here — `Nitrosotalea devaniterrae` -> `Nitrosotalea devanaterra`, `Methylocystis parvus` -> `Methylocystis parva`. So 51 of 138 — 37% — are not reclassifications under any reading, and that is a floor: the 87 "genuinely different" include an unknown number of NCBI renames and spelling variants. Filter on this slot to find "the two labels are not identical", which is what it computes. Do not read it as provenance. #480 narrowed it: dropping the 40 strain-designation cases took the non-reclassification share from 54% to 38% at that time, and the genuinely-different share from 46% to 62%. The current block counts are the ones counted above, not these historical rounded percentages. Polyphyly suffixes are deliberately still reported — `Bacillota` -> `Bacillota_A` is a real GTDB distinction, and #480 records that folding it in here is the arguable middle rather than the obvious next step. An enum (#480 option 3) is where this wants to end up. ONE call site computes it now, `name_differs` (#482). Two used to: `bool(sp and ref and sp != ref)` on the species path, which produced 121 of the then-154, and `top != _clean_label(label)` on the genus-and-higher path. They disagreed — the first had a crosswalk fallback for `ref` and a null-guard returning False where the second returned True, so a missing label read as a name change at genus rank and not at species rank. Counts are pinned by `tests/test_is_reclassified_semantics.py`, which fails when they drift; a count in this text reaches no generated artifact, since pythongen drops attribute descriptions.
GtdbClassification.majority_fractionfloatFraction of genomes under the NCBI taxon that map to this GTDB taxon (0.0-1.0), from the kg-microbe NCBI2GTDB table — a confidence for the mapping. 1.0 means an unambiguous 1:1 correspondence.
GtdbClassification.mapping_sourcestringProvenance of the mapping: the source table and a content digest of it, e.g. "kg-microbe NCBI2GTDB.tsv.gz sha256:761d5537a7edb4b0 (file mtime 2026-07-25)". The digest is what identifies the input -- an earlier form recorded "GTDB release latest (built <mtime>)", where "latest" was a literal nothing read and the mtime is a filesystem attribute rather than a property of the data, so a block that differs from today's crosswalk could not be told from one that is wrong (#624). Blocks written before that change still carry the old string.
GtdbClassification.ncbi_source_idstringThe NCBITaxon id this GTDB classification was mapped from.
GtdbClassification.support_genomesintegerNumber of genomes supporting the chosen GTDB taxon — the numerator behind majority_fraction. The schema bounds this on its own but cannot relate it to total_genomes or majority_fraction: that is cross-field arithmetic, which LinkML's JSON-Schema backend has no way to express (#387, with the spike recorded in the class rules above). `support_genomes: 99, total_genomes: 3` passes `just validate` and is caught by `just validate-gtdb` and by `validate-strict` in CI. Present only on genus-and-higher groundings, where this majority is computed from the mapping rows directly. Absent on species-level groundings: there majority_fraction comes from the crosswalk's own column, which carries two decimal places, so any numerator derived from it would assert a precision the source lacks (~170 genomes of slack on a 17191-genome taxon).
GtdbClassification.total_genomesintegerNumber of genomes the majority was computed over — the denominator behind majority_fraction, and the answer to "0.571 of what?". For genus-and-higher, the genomes across every candidate GTDB taxon at that rank, excluding rows dropped by the named-species filter (sp./uncultured/informal), so it is the evidence actually considered rather than every genome under the NCBI taxon. For species, the genomes in the crosswalk rows this grounding was resolved from — the taxon's own rows when it matched by NCBI id, the name group when it matched by species name. Those scopes differ, so an id-matched block can report far less than the evidence that exists for its species; widening it needs a key as stable as the id, which the crosswalk does not offer (#389). Counted at a single depth: a species-rank row and its strain rows overlap, so the larger of the two is taken and never their sum. Note majority_fraction is rounded, so neither count can be recovered from it.
